# Data lakes: optional alternative, not the third PoC folder
The original ZIP's third folder was `03_Local_PoC`, not a data-lake folder. This folder was added to address the later question about data lakes. A data lake (object storage with files such as Parquet) can serve as a restricted holding or analytics area, but it does not automatically create a relationally consistent, locally restorable PostgreSQL fixture. JSONB, missing parents, history and FK ordering still require explicit handling. A lakehouse table format likewise does not solve defect fidelity or anonymisation by itself. Do not introduce a lake merely for this PoC: it increases infrastructure and governance complexity. Evaluate it only if an approved data platform already exists and a clear reuse case is demonstrated.
